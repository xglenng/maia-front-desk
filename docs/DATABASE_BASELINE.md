# Database baseline and supported migration paths

## Versioned baseline

`packages/db/baseline/pre-journal-schema.ts` preserves the schema from commit `c5048d0`, immediately before the first journal migration. `pre-journal.sql` is generated by the installed Drizzle generator, ordered as tables, indexes, foreign keys, with a source SHA-256. It creates 44 original tables, including all four auth tables. The six immutable journal migrations then produce the current 48 application tables.

This baseline is **only for an empty database**. It is not a repair migration or an existing-database adoption script. No production or Railway database has been inspected or initialized with it. Do not apply it to either existing staging service.

## Supported paths and local evidence

The opt-in `packages/db/__tests__/baseline-postgres.test.ts` uses the real Drizzle migrator in randomly named schemas inside the approved disposable local PostgreSQL cluster. It compares:

1. Empty schema → historical baseline → all six journal entries.
2. Historical baseline → migrations 0000–0002 → inserted synthetic organization → migrations 0003–0005 → repeat migration (no-op).
3. Current generated schema snapshot.

Columns (types/defaults/nullability), structural constraints (including delete actions), and structural indexes match across all three paths. Physical column ordering and generated constraint/index names are excluded; these differ without changing query behavior. Six journal records are verified and synthetic data is preserved. The test rewrites only explicit public-schema references to its isolated schema in temporary migration files; it does not rewrite repository migrations or infer a deployed journal.

Repeat locally only after starting the disposable cluster with TCP disabled:

```sh
MAIA_BASELINE_TEST_SOCKET=/private/tmp/maia-signup-JmakBr node --import tsx --test packages/db/__tests__/baseline-postgres.test.ts
```

## Installation and rollout gates

A future approved empty deployment needs: verified empty database and separate credentials; transactionally install the versioned baseline; run the existing Drizzle journal; verify schema and journal. The baseline must not be marked as journal entry 0000: that entry is the studio configuration migration and must actually execute. No automatic production installer or DATABASE_URL fallback has been added.

Existing installations require separately approved, read-only verification of their actual schema and journal before selecting an upgrade. A schema produced by `db:push`, auth setup SQL, or a current snapshot cannot be assumed to match the supported baseline or journal. Do not forge journal rows or replay the entire journal on current-schema staging. Snapshot adoption and upgrade of the existing synthetic Railway database remain pending.

## Drift corrected locally

Drizzle declarations now include the migration's appointment revision check, payment confirmation-method check, and appointment automation index. Studio location references use the migration's composite tenant FK without redundant snapshot-only single-column references (whose SET NULL action conflicted with composite CASCADE). Existing migration files remain unchanged; no new migration is necessary for databases already installed through this journal. Databases built by other paths require inspection before any corrective DDL.

## Rollback

Apply a baseline only transactionally to a verified empty target; rollback a failed initialization instead of dropping user data. Drizzle forward migration execution is transactional in the tested path. Never remove applied journal records to force replay. For an approved deployed upgrade, take and verify a backup and coordinate application compatibility; prefer a reviewed forward correction. Restoring a backup can lose later writes and requires explicit approval. No automated destructive rollback is supplied.
